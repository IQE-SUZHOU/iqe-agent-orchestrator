### 1.3 Routing key 规则（真实发布用的字符串）

| 消息 | routing key | 拼出处 |
|---|---|---|
| 命令 | `ci.cmd.<stage>.<mode>` | `dispatch.py:150-152`（`f"ci.cmd.{stage}.{action}"`，`action = mode`） |
| 只投不等（故障注入） | `ci.cmd.<stage>.<mode>` | `dispatch.py:237-241`，mode 必须取 `payload.mode` |
| 结果 | `ci.result.<stage>` | `bus.py:83-95` `publish_result()` |
| 事件 | `ci.event.<...>`（见 §6） | `dispatch.py:363-375` |
| 死信 | `ci.dlq.<stage>` | `bus.py:109`（队列参数 `x-dead-letter-routing-key`） |

> ⚠️ **`envelope.subject_of()` 不能当 routing key 用**。它给 result 拼的是 `ci.result.<stage>.<status>`
> （4 段，`envelope.py:219-220`），而 `q.orch.results` 的绑定是 `ci.result.*`（只匹配 3 段）——照它发布，
> 结果消息会**没有任何队列接收**。这个函数只用于日志展示。

### 1.4 账号与权限矩阵（强约束在 write 上）

| 账号 | configure | write | read |
|---|---|---|---|
| `ci_orch` | `^(ci\.(cmd\|result\|event\|dlx)\|q\.(orch\|dlq\|audit)[.a-z_]*\|q\.agent\.[a-z]+)$` | `^(ci\.(cmd\|event\|dlx)\|q\.(agent\.[a-z]+\|orch\.(results\|events)\|dlq\|audit\.[a-z]+))$` | 上述全部 |
| `ci_agent_<stage>` | `^(q\.agent\.<stage>\|ci\.result)$` | `^ci\.result$` | `^q\.agent\.<stage>$` |

⇒ **Agent 在物理上无法命令另一个 Agent，也无法读别人的队列**（`setup_broker.py:81-115`）。
`ci_orch` 的 read 里含 exchange、write 里含 queue，是因为 RabbitMQ 把 `queue.bind` 记为「对队列 write + 对 exchange read」。

## 2. 信封契约（所有跨单元消息的唯一载体）

Schema：`common/data/schemas/envelope.schema.json`；构造与校验：`common/envelope.py`。

### 2.1 通用字段

|---|---|---|---|---|

| `msg_type` | `command` \| `result` \| `event` \| `control` | ✅ | 生产方 | `control` 在枚举里但**当前无生产方** |

| `scenario_hint` | string ≤64 \| null | — | 编排层 | Mock 剧本选择；生产为 null |
| `payload` | object | ✅ | 双方 | 见 §2.2 / §2.3 |
| `evidence_refs` | array ≤50 | — | Agent | 与 `payload.evidence_refs` 同步写（`envelope.py:161-163`） |

### 2.2 命令的 payload（编排层 → Agent）

固定形状 `{"mode": "<mode>", "input": {…}}`（`dispatch.py:117`），其中 `mode` 由
`make_command()` 的 `setdefault("mode", …)` 兜底（`envelope.py:128`）。
`input` 的形状由 §4 各阶段表给出，Agent 侧**硬校验**（`runtime.py:288-300`）。

### 2.3 结果的 payload（Agent → 编排层）

| 字段 | 类型 / 枚举 | 必填 | 说明 |
|---|---|---|---|
| `payload.stage` | 8 个 stage 名 | ✅ | 与信封 `stage` 一致 |
| `payload.attempt` | int ≥1 | ✅ | 回显命令的 attempt |
| `payload.status` | `ok` \| `retryable` \| `blocked` \| `expired` | ✅ | 见 §7 处置矩阵 |
| `payload.duration_ms` | int | 生成时总带上 | `age_ms(command)`（`envelope.py:154`） |
| `payload.output` | object | **status=ok 时必填** | 出参，形状见 §4 |
| `payload.error` | object（`code` 必填，`detail` ≤1000） | **retryable / blocked / expired 时必填** | `code` ∈ `timeout` `mock_fault` `schema_invalid` `schema_mismatch` `no_evidence` `disabled` `source_unavailable` `quota_exceeded` |
| `payload.evidence_refs` | array | — | 取证引用（DB 里的 URI） |

> 注意：`rejected` **不在** result 状态词表里——入参违约 / 毒消息不回 result，直接 `nack(requeue=False)` 进 DLQ（§3）。

## 3. 一次往返的完整时序（含校验链与投递语义）

```
编排层 dispatch()                      Agent _handle()
  │ 1. stage_runs 开记录 (open)          
  │ 2. pending[idempotency_key] = Future
  │ 3. publish ci.cmd → publisher confirm
  │──────────────────────────────────────▶ 4. load() 信封 schema 校验 ── 失败 → nack→DLQ
  │                                        5. msg_type/stage 不属于我 → ack 丢弃
  │                                        6. age_ms > ttl_ms → result(expired) + ack
  │                                        7. 幂等层 2：has_result(key) → ack 跳过
  │                                        8. 幂等层 1：claim(key) 抢锁失败 → ack 跳过
  │                                        9. 入参契约校验（mode 归属 + input schema）
  │                                           ── 失败 → nack→DLQ（不回 result）
  │                                       10. 跑剧本 → 出参软校验（只告警）
  │ 11. ◀── publish ci.result（先等 confirm）
  │                                       12. 再 ack 命令消息
  │ 13. _on_result 按 idempotency_key 找 Future → set_result
  │     找不到 → ci_late_or_duplicate_results_total + stage_run_mark_late
  │ 14. 任何异常都 ack（否则 prefetch 会把后续投递全卡住，dispatch.py:249）
```

**投递语义 = 至少一次 + 双层幂等**：先发布 result 再 ack 命令（`runtime.py:3-5` 注释、`runtime.py:252-253`），
所以 Agent 崩在中间会被 broker 重投；重复由 `msg_dedup` 表的 `claim()` 抢锁 + `has_result()` 吸收
（`db.py:84-100`，`runtime.py:176-186`）。

**编排层超时**：`asyncio.wait_for(fut, timeout)`，timeout = step 的 `timeout_s` 或 `STAGE_TIMEOUT_S=30s`
（`dispatch.py:130,169`；`config.py:65`）。超时后**编排层自己合成**一条 `status=retryable, code=timeout`
的结果并落库 `stage_runs.status='timeout'`（`dispatch.py:170-181`）——Agent 稍后迟到的结果走
`stage_run_mark_late`，不会覆盖。

## 6. 事件契约（`ci.event`）

只有编排层发事件；Agent 不发。全仓穷举（排除 `build/`）后，调用点只有 4 处，其中 1 处是发布器本身：

- 发布器：`BusGateway.publish_event()` → `make_event(...)` → `ci.event`（`dispatch.py:363-375`）
- 调用者只有 3 个：`scan.py:79`、`graph.py:537`、`graph.py:734`（下表）

| routing key | 触发时机 | payload 关键字段 | 出处 |
|---|---|---|---|
| `ci.event.case.created` | 巡检提升出新 Case | `scan_id`、`case_id`、`job`、`signal` | `scan.py:79-80` |
| `ci.event.case.<status>` | 每个 step 成功后（status = 该步设置的 Case 状态） | `stage`、`mode`、`step_id`、`verb` | `graph.py:537-542` |
| `ci.event.case.<status>` | Case 终态（`closed` / `closed_rejected` / `blocked`） | `status`、`terminal_from`、`blocked_reason` | `graph.py:734-739` |

消费者：`q.orch.events` 只计数 + 打日志（`dispatch.py:347-361`）；`q.audit.events` **没有消费者**，纯留档。

> （`grep -rn "ci.event.case\|case.created" tests/` 为空）。事件的兼容性目前只靠代码约定，
> 改事件名不会有测试报错。

## 7. 失败与状态处置矩阵

| 来源 | `status` | Agent 动作 | 编排层动作 | `stage_runs.status` | 是否重试 |
|---|---|---|---|---|---|
| 剧本成功 | `ok` | 发 result + ack | 取 `verb` → 路由下一步 | `done` | — |
| 注入故障 / 剧本抛异常 | `retryable` | 发 result（`error.code`，异常统一 `mock_fault`）+ ack | 本步内重试，`attempt+1` | `failed` | ✅ 至 `max_attempts`（默认 `STAGE_MAX_ATTEMPTS=2`，`config.py:66`；`graph.py:473,506`） |
| 环境/机器不可用 | `blocked` | 发 result + ack | 不重试；Case 走 blocked 收敛 | `blocked` | ❌ |
| 消息在队列里超过 `ttl_ms` | `expired`（`error.code=timeout`） | 不跑剧本，直接回 + ack（`runtime.py:163-173`） | 等同 retryable | `expired` | ✅ |
| 编排层等不到结果 | 编排层合成 `retryable/timeout` | — | 落 `timeout` 记录（`dispatch.py:170-181`） | `timeout` | ✅ |
| 信封不合 schema / `msg_type` 或 `stage` 不属于我 / mode 不属于本 stage / input 违约 | **不发 result** | `nack(requeue=False)` → `ci.dlq.<stage>`（`runtime.py:134-139,202`） | 消费 `q.dlq` → 落 `dlq` 表 | 不产生终态（pending 等到超时） | ❌ |
| 迟到/重复结果 | 已 ack 的重复投递 | 幂等层吸收 | `ci_late_or_duplicate_results_total` + `stage_run_mark_late` | 不覆盖 | — |

DLQ 落库字段：`stage, idempotency_key, case_id, reason, original_routing_key, redelivered, body(≤4000)`
（`dispatch.py:322-333`）。`reason` 优先取 `x-death[0].reason`，否则 `contract_violation: <错误>`
（`dispatch.py:40-67`）；原始 rk 从 `x-death[0].routing-keys`（**复数数组**，RabbitMQ 4.3.6 实测没有单数
`routing-key`）取（`dispatch.py:304-314`）。

## 8. 可靠性与幂等要点

1. **持久化**：所有消息 `delivery_mode=PERSISTENT`、队列/exchange 全 `durable`（`bus.py:66-74,131-160`）。
2. **publisher confirm**：channel 开 `publisher_confirms=True`，`publish()` 会等 confirm（`bus.py:120,80-81`）——
   编排层 `cmd_published` 日志出现即代表 broker 已收。
3. **两套 TTL，语义不同**：队列级 `x-message-ttl=3600000`（1 h，过期即丢弃/死信）与信封 `ttl_ms`
   （默认 900 s，Agent 自己判断"太老了不重跑"）。改一个不影响另一个。
4. **幂等键即全链路主键**：`<case_id|run_id>:<step_id>:<attempt>` 同时用于 Agent 去重（`msg_dedup`）、
   `stage_runs` 主记录、编排层 pending future 关联、消息 header `idempotency_key`。
5. **attempt 语义**：Case 生命周期内单调递增，回炉（`jump`）后再次进入同一步时 **不重置**
   （`graph.py:462-465`），所以同一步的幂等键不会撞。信封 schema 上限 5。
6. **prefetch 即并发度**：慢阶段（reproduction/triage/reviewer 4）不与快阶段互相阻塞（`bus.py:26-32`）。
7. **拓扑声明权限集中在编排层**：Agent 用 `passive=True` 声明队列，队列不存在就**启动即失败**
   （`runtime.py:99-100`、`bus.py:173-175`），不会静默自建错拓扑。

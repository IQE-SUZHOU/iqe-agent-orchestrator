# 05 数据模型、部署与演示

## 1. Postgres 模型（实现对照：11 张表）

> **权威 DDL 是 `orchestrator/src/iqe_orchestrator/migrations/001_init.sql`**（幂等、可重复执行）。本节是设计视图：实现里共 **11 张表** —— `cases / scans / stage_runs / evidence / tickets / reviews / daily_reports / msg_dedup / workflows / plans / dlq`，比下面这段多了 `scans` 与 `dlq`（见 §1.4）；列级差异已就地标注。

```sql
-- 1. Case：全生命周期实体
create table cases (
  case_id       text primary key,
  run_id        text not null,
  scan_id       text,                              -- 来自哪一轮扫描（实现有此列）
  source        text not null default 'mock',      -- mock | jenkins(未来)
  job           text not null,
  build         bigint,
  signal        text not null,                     -- none | error
  signature     text,
  status        text not null,                     -- 见 01 §5 状态机
  workflow_key  text,                              -- 触发声明或命中 registry 的 key
  plan_id       text,                              -- 见 plans
  plan_source   text,                              -- workflow | llm（见 03 §2.1）
  priority      int  not null default 1,
  scenario_hint text,                              -- Mock 剧本透传（实现有此列）
  progress      jsonb not null default '{}',       -- {gen, replayed_at, review_loop_seq, jump_count}
  blocked_reason text,                             -- 熔断原因（实现有此列）
  payload       jsonb not null default '{}',       -- Monitor observation 原文
  case_report   jsonb,                             -- reporting(mode=case) 的结案报告（实现后加列）
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
create index on cases (status);
create index on cases (signature);
create index on cases (created_at desc);
create index on cases (plan_source);

-- 2. 阶段执行：交互演示的核心账目（每一次命令/结果都留一行）
create table stage_runs (
  id            bigserial primary key,
  case_id       text references cases(case_id) on delete cascade,  -- 可空：Monitor 扫描/日报的行没有 Case
  run_id        text not null,
  scan_id       text,                              -- 只有扫描产生的行有值
  stage         text not null,                     -- monitor|triage|reproduction|ticket|review|reporting
  step_id       text not null,                     -- 计划里的 step id；Monitor 固定 'scan'，日报固定 'daily1'
  mode          text,                              -- 以 stage 契约为准：monitor=scan / triage=full|classify_only
                                                   --   / reproduction|ticket|review=run / reporting=case|daily
  attempt       int  not null default 1,           -- 单调递增，规则见 03 §8.3
  status        text not null default 'dispatched',-- dispatched|done|blocked|failed|expired|timeout|late（03 §8.4）
  idempotency_key text not null unique,            -- 幂等层 3
  started_at    timestamptz not null default now(),
  finished_at   timestamptz,
  latency_ms    int,
  output        jsonb,                             -- Agent result.output
  error         jsonb
);
create index on stage_runs (case_id, started_at);
create index on stage_runs (stage, started_at desc);
```

> **实现里没有 `running` / `skipped` 这两个 stage_runs 状态**：`stage_runs` 只有编排层写（`orchestrator/src/iqe_orchestrator/common/db.py:138`），取值集合就是上面注释里那 7 个；终态映射见 03 §8.4。Monitor 扫描产生的行是 `case_id=NULL` + `scan_id` 非空 + `step_id='scan'` + `attempt=1`（见 02 §7、03 §8.3）。

-- 3. 证据（演示存正文，生产换对象存储 URI）
create table evidence (
  id          bigserial primary key,
  case_id     text not null references cases(case_id) on delete cascade,
  stage       text not null,
  kind        text not null,                       -- distilled_log|jarvis|junit|history|artifact
  uri         text not null,                       -- db://evidence/<id> 或未来 minio://…
  meta        jsonb not null default '{}',
  body        text,
  created_at  timestamptz not null default now()
);
create index on evidence (case_id, stage);

-- 4. 工单（一 Case 一后端只允许一张）
create table tickets (
  id           bigserial primary key,
  case_id      text not null references cases(case_id) on delete cascade,
  backend      text not null,                      -- jira | azure
  external_key text,
  url          text,
  ticket_status text not null,                     -- draft|created|linked_duplicate
  duplicate_of text,
  ticket_priority text, assignee_team text,
  payload      jsonb not null default '{}',
  created_at   timestamptz not null default now(),
  unique (case_id, backend)
);

-- 5. 复核结论
create table reviews (
  id          bigserial primary key,
  case_id     text not null references cases(case_id) on delete cascade,
  verdict     text not null,                       -- approve|needs_info|reject
  reason_code text, requested_info jsonb, checks jsonb, quality jsonb,
  loop_seq    int not null default 1,
  created_at  timestamptz not null default now()
);

-- 6. 日报 + 指标
create table daily_reports (
  day         date primary key,
  report_md   text,
  metrics     jsonb not null default '{}',
  cases       jsonb not null default '[]',         -- 已验证 Case 素材区
  published_at timestamptz
);

-- 7. 消息去重账
create table msg_dedup (
  dedup_key   text primary key,                    -- = idempotency_key
  stage       text, seen_at timestamptz not null default now()
);
create index on msg_dedup (seen_at);

-- 8. workflow 定义（workflows/*.yaml 为源，本表是运行时快照 + 匹配规则）
create table workflows (
  key          text primary key,                   -- s1_lite | s2_full | warming | ...
  version      int  not null default 1,
  title        text not null,
  enabled      boolean not null default true,
  priority     int  not null default 100,          -- 多条 match 命中时取大者
  match        jsonb not null default '{}',        -- {signal: none|error, workflow_key: [...]}
  steps        jsonb not null,                     -- 与 plan.steps 同构
  yaml_path    text not null,                      -- common/data/workflows/<key>.yaml
  yaml_sha256  text not null,
  loaded_at    timestamptz not null default now()
);

-- 9. 运行期计划（文件是真相：PLANS_DIR/<case_id>/<plan_id>.yaml；本表只存索引）
create table plans (
  plan_id      text primary key,
  case_id      text not null references cases(case_id) on delete cascade,
  run_id       text not null,
  version      int  not null default 1,
  source       text not null,                      -- workflow | llm
  workflow_key text,
  degraded     boolean not null default false,     -- true=LLM 两次校验失败后的内置安全网
  path         text not null,
  yaml_sha256  text not null,
  rationale    text,
  model        text,
  confidence   numeric,
  prompt_hash  text,
  validator    text not null,                      -- plan-validator/v1
  created_at   timestamptz not null default now(),
  unique (case_id, version)
);
create index on plans (source, created_at desc);
```

> LangGraph 的 `langgraph_checkpoint*` 表由 checkpointer 自动建（`AsyncPostgresSaver.setup()`），与上面同库不同前缀。

### 1.4 实现多出的两张表（设计稿此前漏列）

```sql
-- 扫描台账：每轮 Monitor 扫描一行（POST /api/scan 与定时扫描都写它）
create table scans (
  scan_id     text primary key,
  run_id      text not null,
  scenario    text,
  started_at  timestamptz not null default now(),
  finished_at timestamptz,
  status      text not null default 'running',        -- running | done | failed
  counts      jsonb not null default '{}',            -- {feed, new_cases, observed_only, suppressed, …}
  error       jsonb
);

-- 死信归档：q.dlq.<stage> 里的消息落库，供 GET /api/dlq 与演示 D5 取证
create table dlq (
  id                   bigserial primary key,
  stage                text,
  idempotency_key      text,
  case_id              text,
  reason               text,   -- 编排层自判：envelope_invalid / expired / contract_violation: … / x-death reason / consumer_rejected
  original_routing_key text,   -- 例如 ci.cmd.review.run
  redelivered          boolean not null default false,
  body                 text,
  created_at           timestamptz not null default now()
);
```

其余列级差异（都以 `orchestrator/src/iqe_orchestrator/migrations/001_init.sql` 为准）：

| 设计稿写法 | 实现 | 为什么 |
|---|---|---|
| `evidence.case_id not null` | 可空，另加 `scan_id` | Monitor 产出的证据还没有 Case |
| `tickets` 有 `id` 主键 | 无 `id`，靠 `unique (case_id, backend)` | 一 Case 一后端一张单，天然唯一 |
| `msg_dedup.seen_at` | `stage / consumed_by / created_at`（索引在 `created_at`） | 记录"谁消费了这条键"，便于排重复投递 |
| `workflows.yaml_path / yaml_sha256 / loaded_at` | `source / updated_at` | registry 快照用 `source='file'` 标记 |
| `plans.path / version / run_id / confidence / prompt_hash` + `unique(case_id, version)` | `file_path / steps`，无版本唯一约束 | 重放生成新 `plan_id`，同一 Case 多行按 `plan_id` 区分（见 03 §8.3） |
| `daily_reports.published_at` 可空 | `not null default now()` | 写库即发布 |

**实现对照（`deploy/k8s/`、`deploy/deploy.sh`）**：

- **中间件不自建**：演示复用集群里已有的 RabbitMQ 与 Postgres（`infra-database` 命名空间），只新增 vhost `ci`、7 个账号与库 `ci_triage`（`tools/setup_broker.py` + `orchestrator/migrate.py`）。所以 `00-infra.yaml` 里只有 Namespace / Secret / ConfigMap，没有 message-bus 与 state-store 两个 Deployment。
- **一个镜像跑 7 个单元**：`172.31.0.3:7777/library/ci-triage:<tag>`，靠 `command` 区分（`python -m orchestrator.main` / `python -m agents.<stage>.main`）；Agent 单元名是 `agent-monitor / agent-triage / agent-reproduction / agent-ticket / **agent-review** / agent-reporting`（不是 `agent-reviewer`）。
- **端口**：所有单元的容器端口都是 **8080**（不是 8081）；对外入口是 Service `ci-triage-ui` 的 NodePort **30099**（`http://172.31.0.3:30099/`，API 同前缀）。
- **探针**：readiness 打 `/readyz`、liveness 打 `/healthz`（编排层与 Agent 都一样，实现里都有）。
- **plan 目录当前是 `emptyDir`，不是 PVC**（`20-orchestrator.yaml` 挂 `/var/lib/ci-triage`）：Pod 重启会丢封存计划文件，重放只能靠 `plans` 表索引重新实例化。持久化存储是待确认项（见 06 §5）。
- 编排层用 `replicas=1 + strategy: Recreate`（与本文「单活」一致）。
- **env 名以 `orchestrator/src/iqe_orchestrator/common/config.py` 为准**：上表 Agent 一栏里的 `MOCK_FEED_SOURCE`、`CI_DISTILLED_CHARS`、`REVIEW_MODEL`、`RETENTION_DAYS` 在实现中**不存在**（Agent 侧实际只有 `MOCK_SCENARIO / MOCK_DELAY_MS / MOCK_FAILURE_RATE / NOISE_THRESHOLD / REPRO_ENABLED / REPRO_MAX_RUNS / TICKET_BACKEND / TICKET_AUTOCREATE`，全局共用同一份 Config）；`ORCH_PREFETCH=64`、`RECURSION_LIMIT=40`、`TTL_MS=900000`、`SCAN_STARTUP_DELAY_S=30`、`SCHEDULER_ENABLED`、`REPORT_TZ` 见 03 §13 实现对照。

**消息总线容器配置（演示档）**：

```yaml
# deploy/compose.yaml（总线部分）
services:
  rabbitmq:
    image: rabbitmq:4.1-management      # 自带 management UI 与 rabbitmq_prometheus
    hostname: rabbitmq
    environment:
      RABBITMQ_DEFAULT_VHOST: /ci
      RABBITMQ_DEFAULT_USER: ci-admin
      RABBITMQ_DEFAULT_PASS: ${RABBITMQ_PASS:?required}
    ports: ["5672:5672", "15672:15672", "15692:15692"]
    volumes:
      - ./rabbitmq/conf.d:/etc/rabbitmq/conf.d:ro            # 内含 load_definitions 指令
      - ./rabbitmq/definitions.json:/etc/rabbitmq/definitions.json:ro
      - rmq-data:/var/lib/rabbitmq
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "check_port_connectivity"]
      interval: 10s
      timeout: 5s
      retries: 12
volumes:
  rmq-data:
```

> `rabbitmq/conf.d/20-definitions.conf` 只有一行：`load_definitions = /etc/rabbitmq/definitions.json`。
> 演示用 classic durable 队列（单节点不存在复制需求）；生产切 quorum（`x-queue-type: quorum`，3 副本 Raft，原生 `x-delivery-limit`），其余声明不变。

资源估算（演示档）：Agent 各 `256Mi / 0.25 CPU`；orchestrator `512Mi / 0.5 CPU` + `1Gi` PVC（plan YAML）；RabbitMQ `512Mi / 0.5 CPU`；Postgres `1Gi / 1 CPU`。

> `workflows/` 以**read-only ConfigMap/镜像内文件**挂载（人工定义随版本发布）；`plans/` 用**读写 PVC**（运行期产物，文件即真相，DB 只存索引）。

启动顺序与自检：
1. `state-store`、`message-bus` Ready；
2. init Job：导入 `rabbitmq/definitions.json`（exchange/queue/binding/权限）+ 建表（业务表 + `checkpointer.setup()`）；
3. 6 个 Agent 启动并 consume 自己的队列（启动时打印 queue 与 binding，断言存在）；
4. orchestrator 启动时（实现对照 `orchestrator/app.py::lifespan`）：① `declare_topology()` 自己声明 exchange/队列/绑定（**不是**去比对 `definitions.json`，也没有"缺配即退出"的自检），随后 `load_registry()` 加载 `workflows/*.yaml` 并逐条 upsert 进 `workflows` 表——**解析失败的那一条被跳过并记 `workflow_load_failed` 日志**（"任一条不合法即整体拒绝启动"是设计目标，见 06 §5）；② 打开 checkpoint 连接池并 `AsyncPostgresSaver.setup()`；③ 置 `RT.ready=True`，`/readyz` 才开始返回 ready。
5. orchestrator 单活：K8s 用 `replicas=1 + Recreate`；本地演示直接单进程。

compose/K8s 只在此文档中作为拓扑说明，实施阶段再落文件（见 06 §4）。

## 4. 演示脚本（交互功能的完整验收）

前置：`docker compose up`（或 `bash scripts/run_local.sh`），`GET :8080/readyz` 返回 `{"status":"ready", …}` 才算全绿（`/healthz` 只表示进程活着，`/readyz` 才表示总线/DB/计划层都接好了）。

| # | 演示 | 操作 | 期望证据 |
|---|---|---|---|
| **D1** | **场景 1（无报错 → 只 Monitor+Triage）** | feed 只放 `signal=none` 构建 → `POST /api/scan`（body 可带 `{"scenario": "…"}`） | `trace` 只有 2 行 stage_runs（monitor、triage mode=classify_only）；Case 终态 `triaged`；无 `tickets` 行；`q.agent.reproduction` 的发布计数为 0（Prometheus `rabbitmq_queue_messages_published_total{queue="q.agent.reproduction"}` / UI 的 `message_stats.publish`） |
| **D2** | **场景 2（有报错 → 6 段完整串行）** | feed 含 1 条 error，`MOCK_SCENARIO=approve` → `POST /api/scan` | trace 6 行、顺序严格 monitor→triage→reproduction→ticket→review→reporting；`tickets` 1 行；`daily_reports.cases` 含该 Case；全程同一 `correlation_id` |
| **D3** | **回炉回路** | `MOCK_SCENARIO=needs_info`（reviewer）+ 第二次 `approve` | trace 中 `triage` 出现 2 次（attempt 各 1）；`reviews.loop_seq=1,2`；终态 `closed` |
| **D4** | **驳回不开单** | `MOCK_SCENARIO=reject` | `tickets` 无行；终态 `closed_rejected`；出现在日报 OPEN 清单 |
| **D5** | **超时/失败重试与熔断** | `agent-reproduction` 设 `MOCK_FAILURE_RATE=0.6` 或 `STAGE_TIMEOUT_S=1` | trace 里 reproduction 两行 attempt=1,2，`status` 分别是 `timeout`（无结果）或 `failed`（`retryable` 落库映射）；Case 终态 `blocked`（`blocked_reason` 写明是哪一步耗尽）；`q.dlq.<stage>` 有归档、`dlq` 表多一行（`reason` 由编排层判，见 02 §6.4）；流水线其余 Case 不受影响 |
| **D6** | **重复投递幂等（+ 崩溃后的处置）** | 对同一 `idempotency_key` 手动重投一次命令（`POST /api/ops/inject {"kind":"duplicate_command", …}`）；另可 `docker kill orchestrator` 后重启 | 重投不产生第二次副作用：Agent 幂等层吸收，`tickets` 仍只有 1 行，`stage_runs` 该键只有 1 行；**注意**：进程崩溃时 V1 没有自动续跑（03 §9「恢复扫描」未实现），在飞的 Case 靠 `POST /api/cases/{id}/replay` 重新推进，重放后 `progress.gen` +1、新记录的 attempt 从库里播种 |
| **D7** | **每日报告** | `POST /api/report/daily`（body `{"day":"2026-11-25"}`）→ `GET /api/daily-report?day=2026-11-25` | `daily_reports.report_md` 含失败数 / RCA 分布 / TAT / OPEN 清单 / 高频签名 |
| **D8** | **规定触发优先** | 放一个 `workflows/<key>.yaml`（其 `match` 命中该场景，例如 `match.signal: error` + `job_pattern`）→ `POST /api/scan {"scenario": "…"}`。注意：**入参没有 `workflow_key`**，命中靠 `match` + `priority`（`plan.py::match`） | `plans.source=workflow`、`workflow_key=<key>`；`ci_llm_plan_calls_total` **不增加**；trace 步数与 steps 一致 |
| **D9** | **未定义 → LLM 兜底** | 删掉那条 `workflows/<key>.yaml`（让 match 落空），`PLAN_MOCK_SCENARIO=warming_ok`，同一触发 | `plans.source=llm`；`GET /api/cases/{id}/plan.yaml` 可下载同构 YAML；`rationale` 非空；执行路径与 D8 等价但来源不同 |
| **D10** | **LLM 计划非法 → 安全网** | `PLAN_MOCK_SCENARIO=skip_review`（报告前无复核，违反 V4） | `ci_llm_plan_calls_total{result="invalid"}=1`；重试 1 次仍失败 → `degraded=true`、`workflow_key=s2_full`；6 段完整执行；`decisions` 含 `plan_degraded` |
| **D11** | **统一校验器拦下人工 YAML** | 放入 `bad.yaml`（`jump` 指向自身，违反 V5）→ 重启编排层 Pod（V1 **没有** `POST /admin/workflows/reload`） | 该条被跳过并记 `workflow_load_failed` 日志（`plan.py:199-203`），其余 workflow 照常加载；`GET /api/workflows` 里不出现 `bad`；"任一条不合法就整体拒绝启动"是设计目标，见 06 §5 |

验收判据（交互层）：
- **分支正确**：S1 绝不触发 3–6 阶段命令；S2 必须 6 阶段齐全且顺序唯一。
- **消息可观测**：每个阶段能在 `stage_runs` 找到「命令 attempt + 结果 + latency」，且 `correlation_id` 贯穿。
- **幂等成立**：D6 中重复投递不产生重复副作用（重复建单 / 重复复现）。
- **故障隔离**：任一 Agent 失败只影响该 Case 的该阶段，不阻塞其他 Case。
- **计划闸门**：凡进入执行的计划必有 `plans` 行 + `path` 文件 + 非空 `validator`；非法计划**从未**产生 `stage_runs`。
- **来源可审计**：`cases.plan_source` 与 `plans.source` 一致；D8 全程零 LLM 调用，D9 恰好 1 次。

## 6. 安全与护栏（演示档最小）

- 密钥全部走 env / K8s Secret；日志中禁止打印 token（SDK 统一脱敏）。
- Agent 出网白名单：Mock 阶段只需 RabbitMQ(`5672`) + Postgres。
- Broker 最小权限：Agent 账号只能 read 自己的队列 `q.agent.<stage>`、write `ci.result`，**无 `ci.cmd` 权限，也没有 `ci.event` 写权限**（实现见 `tools/setup_broker.py:52-71`：只有编排层账号 `ci_orch` 能 write `ci.cmd|ci.event|ci.dlx`。设计里"ticket/reporting 额外 write `ci.event`"是预留，V1 未授予，见 02 §9）。
- 破坏性动作默认关闭：`REPRO_ENABLED=false`、`TICKET_AUTOCREATE=false` 为生产默认；演示脚本显式打开。
- 计划安全：plan/workflow YAML 用 `yaml.safe_load`（禁 tag/锚点/多文档），防灌水目前靠校验器硬上限（`steps ≤ MAX_PLAN_STEPS=8`、`rationale ≤ 500` 字、`step.id ≤ 16` 字符）而不是文件字节数；`workflows/` 只读挂载；`plans/` 由 `PlanStore.seal()` 写入即封存（`plan.py:321-333`），改流程只能改 registry 或重放生成新 `plan_id`。
- Agent 的写库范围只有 `evidence` 与 `msg_dedup`（幂等 claim）；**`stage_runs` 只有编排层写**（`orchestrator/src/iqe_orchestrator/common/db.py:138`），工单/复现动作只经各自工具桩。

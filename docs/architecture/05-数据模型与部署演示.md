# 05 数据模型、部署与演示

## 1. Postgres 模型（15 张表）

> **权威 DDL 是 `orchestrator/src/iqe_orchestrator/migrations/001_init.sql`**（幂等、可重复执行）。
> 本节是设计视图；表结构与代码不一致时以 DDL 为准。

| 表 | 谁写 | 存什么 |
|---|---|---|
| `cases` | 编排层 | Case 全生命周期：触发信息、状态、计划来源、`progress` 投影（cursor / step_status / loops）、`blocked_reason`、结案报告 |
| `scans` | 编排层 | 每轮扫描一行：场景、耗时、`counts`（观测/新建/抑制） |
| `stage_runs` | 编排层 | 每一次命令一行：`step_id` `mode` `attempt` `status` `idempotency_key` `latency_ms` output/error |
| `evidence` | Agent（+编排层写审计） | 一条动作一条证据：`stage` `kind` `uri` `meta` `body` |
| `reviews` | 编排层 | 三道闸门的结论：`gate` `verdict` `reason_code` `requested_info` `checks` `quality` `loop_seq` |
| `remediations` | 编排层 | 4a 修复：`change_type` `target` `fixed` `work_item_key` `risk` `diff_summary` |
| `verifications` | 编排层 | 4b / 5a：按 `(case_id, mode)` 一行，`reproducible` `fix_verified` `attempts` `payload` |
| `regressions` | 编排层 | 5b / 6c：按 `(case_id, mode)` 一行，`is_regression` `guilty_commit` `guilty_pr` `confidence` |
| `tickets` | 编排层 | 7b：`backend` `external_key` `ticket_status` `duplicate_of` `assignee_team` `payload` |
| `kb_entries` | 编排层 | 知识条目：`kind`（`failure` / `fix` / `guilty_patch`）`component` `signature` `summary` |
| `plans` | 编排层 | 封存索引：`source` `workflow_key` `degraded` `file_path` `yaml_sha256` `validator` `steps` |
| `workflows` | 编排层 | registry 快照：`key` `priority` `match` `steps` `version` |
| `daily_reports` | 编排层 | 日报：`day` 主键 + `report_md` `metrics` `cases` |
| `msg_dedup` | Agent | 消息级幂等 claim：`dedup_key` `stage` `consumed_by` |
| `dlq` | 编排层 | 死信归档：`stage` `reason` `original_routing_key` `body` |

`langgraph_checkpoint*` 表由 `AsyncPostgresSaver.setup()` 自动创建，同库不同前缀。

### 1.1 关键表

```sql
create table cases (
  case_id       text primary key,
  run_id        text not null,
  scan_id       text,                              -- 来自哪一轮扫描（日报/直接触发时为空）
  source        text not null default 'mock',      -- mock | jenkins(未来)
  job           text not null,
  build         integer,
  signal        text not null check (signal in ('none','error')),
  signature     text,
  status        text not null,                     -- 见 01 §5 状态机
  workflow_key  text,                              -- 命中 registry 的 key（degraded 时是内置 key）
  plan_id       text,
  plan_source   text,                              -- workflow | llm
  priority      integer not null default 1,
  scenario_hint text,                              -- Mock 剧本透传
  progress      jsonb not null default '{}',       -- {cursor, plan_steps, step_status, attempts,
                                                   --  completed, loops, review_loop_seq, gen, …}
  payload       jsonb not null default '{}',       -- Monitor observation 原文
  blocked_reason text,
  case_report   jsonb,                             -- reporting(case) 的结案报告
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

create table stage_runs (
  id              bigserial primary key,
  case_id         text references cases(case_id) on delete cascade,  -- 可空：扫描/日报没有 Case
  run_id          text not null,
  scan_id         text,
  stage           text not null,                   -- 8 个 Agent 名
  step_id         text not null,                   -- 计划里的 step id；扫描固定 'scan'，日报 'daily1'
  mode            text,                            -- monitor=scan / reviewer=gate1|gate2|gate3 / …
  attempt         integer not null default 1,      -- Case 生命周期内单调递增（03 §8.3）
  status          text not null default 'dispatched', -- dispatched|done|blocked|failed|expired|timeout
  idempotency_key text not null unique,
  started_at      timestamptz not null default now(),
  finished_at     timestamptz,
  latency_ms      integer,
  output          jsonb,
  error           jsonb
);
```

### 1.2 12 阶段新增的四张表 + `reviews.gate`

```sql
-- reviews 增加 gate 列：同一 Case 会依次过 gate1 / gate2 / gate3，按 (case_id, loop_seq) 有序
alter table reviews add column if not exists gate text;

create table remediations (            -- 4a
  case_id text primary key, change_type text, target text,
  fixed boolean not null default false, work_item_key text, risk text,
  diff_summary text, payload jsonb not null default '{}', created_at timestamptz default now()
);

create table verifications (           -- 4b(evidence) / 5a(verify)
  case_id text not null, mode text not null,
  reproducible text, fix_verified boolean, attempts integer not null default 0,
  payload jsonb not null default '{}', created_at timestamptz default now(),
  primary key (case_id, mode)
);

create table regressions (             -- 5b(check) / 6c(bisect)
  case_id text not null, mode text not null,
  is_regression boolean, guilty_commit text, guilty_pr text, confidence numeric,
  payload jsonb not null default '{}', created_at timestamptz default now(),
  primary key (case_id, mode)
);

create table kb_entries (              -- 2 / 4a / 6c 检索，9 回写
  id bigserial primary key, kind text not null, component text not null,
  signature text, summary text not null, case_id text,
  created_at timestamptz not null default now()
);
create index on kb_entries (component, signature);
```

### 1.3 与早期设计稿的列级差异

| 设计稿写法 | 实现 | 为什么 |
|---|---|---|
| `evidence.case_id not null` | 可空，另加 `scan_id` | Monitor 产出的证据还没有 Case |
| `tickets` 有 `id` 主键 | 无 `id`，靠 `unique (case_id, backend)` | 一 Case 一后端一张单，天然唯一 |
| `msg_dedup.seen_at` | `stage / consumed_by / created_at` | 记录"谁消费了这条键"，便于排查重复投递 |
| `plans.path / version` + `unique(case_id, version)` | `file_path / steps`，无版本唯一约束 | 重放生成新 `plan_id`，同一 Case 多行按 `plan_id` 区分 |
| `daily_reports.published_at` 可空 | `not null default now()` | 写库即发布 |
| 只有 `reviews`（一次复核） | `reviews` + `gate`，外加 `remediations` / `verifications` / `regressions` / `kb_entries` | 12 阶段里三道闸门、两条分支各自需要落点 |

## 3. 部署拓扑（1 编排 + 8 Agent = 9 个 Deployment）

| 单元 | command | 端口 | 副本 | 关键 env |
|---|---|---|---|---|
| `orchestrator` | `ci-orchestrator` | 8080（NodePort 30099） | 1（`Recreate`） | `PLAN_MODE` `MAX_PLAN_STEPS` `MAX_REVIEW_LOOPS` `PLANS_DIR` |
| `agent-monitor` | `ci-agent-monitor` | 8080（健康探针） | 1 | `MOCK_SCENARIO` `NOISE_THRESHOLD` |
| `agent-triage` | `ci-agent-triage` | 同上 | 1 | `NOISE_THRESHOLD` |
| `agent-reviewer` | `ci-agent-reviewer` | 同上 | 1 | `MAX_REVIEW_LOOPS` |
| `agent-remediation` | `ci-agent-remediation` | 同上 | 1 | — |
| `agent-reproduction` | `ci-agent-reproduction` | 同上 | 1 | `REPRO_ENABLED` `REPRO_MAX_RUNS` |
| `agent-regression` | `ci-agent-regression` | 同上 | 1 | — |
| `agent-ticketing` | `ci-agent-ticketing` | 同上 | 1 | `TICKET_BACKEND` `TICKET_AUTOCREATE` |
| `agent-reporting` | `ci-agent-reporting` | 同上 | 1 | `REPORT_TZ` |

* **一个镜像跑 9 个单元**：`command` 区分（`ci-orchestrator` / `ci-agent-<stage>`）。
* **每个 Agent 一份 AMQP 账号**：Secret `ci-triage-credentials` 下 `AMQP_MONITOR` … `AMQP_REPORTING`，
  权限只到自己的队列（write `ci.result`），没有 `ci.cmd` / `ci.event` 写权限。
* **只读资源**：`workflows/` 走 ConfigMap（随版本发布）；`plans/` 用读写 PVC（运行期产物，文件即真相，DB 只存索引）。
* 资源估算（演示档）：Agent 各 `256Mi / 0.25 CPU`；orchestrator `512Mi / 0.5 CPU` + `1Gi` PVC；
  RabbitMQ `512Mi / 0.5 CPU`；Postgres `1Gi / 1 CPU`。

启动顺序与自检：

1. Postgres / RabbitMQ Ready；
2. init Job：`ci-db-migrate` 建表（+ checkpointer `setup()`）、`ci-broker-setup` 声明 exchange/queue/binding/账号；
3. 8 个 Agent 启动并 consume 自己的队列（启动日志打印 queue 与 binding，断言存在）；
4. orchestrator 启动（`app.py::lifespan`）：`declare_topology()` 自声明拓扑 → `load_registry()` 加载
   `workflows/*.yaml` 并 upsert 进 `workflows` 表（**解析失败只跳过该条**并记 `workflow_load_failed`）
   → 打开 checkpoint 连接 → `/readyz` 才返回 ready；
5. orchestrator 单活：`replicas=1 + Recreate`（Dispatch–Await 的 Future 是进程内的）。

## 4. 演示脚本（交互功能的完整验收）

前置：`bash scripts/run_local.sh`（9 个进程）或 `bash deploy/deploy.sh`（K8s），
`GET :8080/readyz` 返回 `{"status":"ready", …}` 才算全绿（`/healthz` 只表示进程活着）。

| # | 演示 | 操作 | 期望证据 |
|---|---|---|---|
| **D1** | 无报错：只观测 | `POST /api/scan {"scenario":"all_success"}` | 命中 `s1_observe_only`；trace = monitor + triage + reporting；终态 `closed`；`tickets` 无行 |
| **D2** | 完整外部链路 | `POST /api/scan {"scenario":"default"}`（1203 是 amdgpu page fault → `rca=driver` → external） | `plan_source=workflow`、`workflow_key=s2_full`；trace 顺序 triage → reviewer:gate1 → reproduction:evidence → regression:check →（bisect）→ ticketing → reviewer:gate3 → reporting；`tickets` 1 行、`verifications` 有 `evidence` 行、`regressions` 有 `check` 行 |
| **D3** | 内部修复分支 | `POST /api/scan` 后用 `scenario_hint=gate1_internal` | `reviews.gate=gate1` 的 `checks` 全过，且 `reviewer:gate1` 的输出 `decision=internal`；走 remediation:fix → reproduction:verify → reviewer:gate2；`remediations.fixed=true`、`verifications.mode=verify` |
| **D4** | 闸门 2 打回（回炉） | `scenario_hint=gate2_rework` | `gate2` 的 `fix_verified` 不过 → `verdict=rework` → `jump r1`；`cases.progress.loops` 出现 `r1:rework`；`reviews.loop_seq` 递增；回炉后 `cursor` 回到 `r1` |
| **D5** | 闸门 3 补件（回炉） | `scenario_hint=gate3_needs_info` | `gate3` 因 `ticket_sections` 不过 → `needs_info` → `jump k1`；ticketing 收到 `requested_focus` 并在 notes 里体现 |
| **D6** | 驳回不开单 | `scenario_hint=gate1_reject` | 闸门 1 `verdict=reject` → `end`；终态 `closed_rejected`；`tickets` 无行 |
| **D7** | 机位不可用（业务阻塞） | `POST /api/scan {"scenario":"blocked_no_machine"}` | reproduction 返回 `status=blocked`；Case 终态 `blocked`、`blocked_reason` 含 `source_unavailable`；**不进 DLQ** |
| **D8** | 超时 → 重试耗尽 → blocked | `POST /api/scan {"scenario":"timeout"}`（或 `STAGE_TIMEOUT_S=1`） | `stage_runs` 里该 step 两行 `attempt=1,2`，`status=timeout`；Case `blocked`；`ci_dispatch_timeouts_total` +2 |
| **D9** | 重复投递幂等 | `POST /api/ops/inject {"kind":"duplicate_command", …}` | 同 `idempotency_key` 不再产生副作用：`tickets` 仍 1 行、`stage_runs` 该键 1 行、`ci_dedup_skip_total` +1 |
| **D10** | 毒消息 → DLQ | `POST /api/ops/inject {"kind":"bad_command", …}` | `q.dlq` 多一条；`dlq.reason=contract_violation: …`；`original_routing_key=ci.cmd.<stage>.<mode>` |
| **D11** | 规定触发优先 | 放一份 `workflows/demo.yaml`（`match.signal: error` + `job_pattern`，`priority` 高于 100）→ 重启编排层 → `POST /api/scan` | `plans.source=workflow`、`workflow_key=demo`；`plans.degraded=false`；无 LLM 调用 |
| **D12** | 未定义 → LLM 兜底 | 删掉 `demo.yaml` 并重启，`PLAN_MOCK_SCENARIO=external_ok`，同一触发 | `plans.source=llm`、`workflow_key=NULL`、`rationale` 非空；`/api/cases/{id}/plan.yaml` 可下载同构 YAML |
| **D13** | LLM 计划非法 → 安全网 | `PLAN_MOCK_SCENARIO=invalid_order`（报告前缺复核，违反 V4） | LLM 重试 1 次仍失败 → `degraded=true`、`workflow_key` 为内置 `s2_full`；trace 里出现 `llm_plan_degraded` |
| **D14** | 校验器拦人工 YAML | 放一份 `bad.yaml`（`jump` 指向自身，违反 V5）→ 重启 | 启动日志 `workflow_load_failed`；`GET /api/workflows` 不含 `bad`；其余 workflow 正常加载 |
| **D15** | 重放 | `POST /api/cases/{id}/replay` | 复用同一 `plan_id` 的封存 YAML（不重新规划）；`progress.gen` +1；新 `attempt` 从库里播种、不与旧幂等键冲突 |
| **D16** | 日报 | `POST /api/report/daily {"day":"2026-11-25"}` → `GET /api/daily-report?day=2026-11-25` | `daily_reports.report_md` 含失败数 / RCA 分布 / 终态分布 / OPEN 清单 |

验收判据：

* **分支正确**：D1 不出现 `reviewer`；D2 的 `reproduction:evidence` 与 `regression:check` 必须相邻；测试类失败（`s3_test_no_repro`）不出现 `reproduction:evidence`。
* **闸门可回炉**：D4/D5 的 `cursor` 必须回退，且回退后 `outputs` 里目标之后的 step 全被清空（UI 上看不到过期的 gate2 结论）。
* **消息可观测**：每个 step 在 `stage_runs` 有"命令 attempt + 结果 + latency"，`correlation_id` 贯穿。
* **写权正确**：`tickets` / `reviews` / `remediations` 等业务表只由编排层写；`evidence` 只由 Agent 写。
* **幂等成立**：D9 重复投递不产生重复副作用；重放（D15）走同一份封存计划。
* **计划闸门**：进入执行的计划必有 `plans` 行 + 封存文件 + 非空 `validator`；非法计划**从未**产生 `stage_runs`。

## 5. 观测（最小集）

**日志**（每服务 JSON stdout）：`ts, level, svc, stage, correlation_id, case_id, event, duration_ms, err`。
关键字：`cmd_published / result_published / step_ok / step_retry / step_result / plan_sealed / plan_jump /
case_finalize / dedup_skip / dlq`。

**指标**（Agent `:8080/metrics`，编排层 `:8080/metrics`）：

| 指标 | 说明 |
|---|---|
| `ci_dispatch_total{stage,mode}` | 编排层下发命令数 |
| `ci_dispatch_wait_seconds` | 单步等待耗时 |
| `ci_dispatch_timeouts_total{stage}` / `ci_dispatch_errors_total{stage}` | 超时 / 下发异常 |
| `ci_results_inbound_total{stage,status}` | 收到的 result 按状态分布 |
| `ci_steps_blocked_total{stage,mode}` | 业务阻塞（重试耗尽） |
| `ci_review_loop_exhausted_total{step}` | 回炉超限 |
| `ci_plan_rejected_total` | 计划被封存前拒掉 |
| `ci_cases_finished_total` / `ci_case_graph_crashes_total` | 终态与图崩溃 |
| `ci_output_contract_violations_total` / `ci_stage_output_violations_total` | 出参契约违规 |
| `ci_dedup_skip_total{stage}` | 消息级幂等命中 |
| `ci_late_or_duplicate_results_total{stage}` | 迟到/重复 result |
| `ci_dlq_total{stage}` | 死信 |
| `ci_scans_total` / `ci_agent_ready_total` | 扫描轮次 / Agent 就绪 |
| `rabbitmq_queue_messages_ready{queue}` / `_unacked` | 队列积压（`:15692` 原生） |

**告警（3 条足够）**：某 stage 失败率 >20%/1h；`q.orch.results` ready > 20 或某 `q.agent.*` 无消费者；
09:00 前当日 `daily_reports` 未生成。

**回放工具**：`GET /api/cases/{case_id}/trace`（读 `stage_runs`）+ Web UI `/ui/cases/{case_id}` +
`q.audit.results` / `q.audit.events`（7d / 30d）+ `GET /api/dlq`。
总线不提供程序化重放；重新推进只有 `POST /api/cases/{case_id}/replay`。

## 6. 安全与护栏（演示档最小）

* 密钥全部走 env / K8s Secret；日志禁止打印 token（SDK 统一脱敏）。
* Agent 出网白名单：Mock 阶段只需 RabbitMQ(`5672`) + Postgres。
* Broker 最小权限：Agent 账号只能 read `q.agent.<stage>`、write `ci.result`，**无 `ci.cmd` / `ci.event` 写权限**；
  只有编排层账号能 write `ci.cmd|ci.event|ci.dlx`（见 `tools/setup_broker.py`）。
* 破坏性动作默认关闭：生产默认 `REPRO_ENABLED=false`、`TICKET_AUTOCREATE=false`；演示脚本显式打开。
* 计划安全：YAML 一律 `yaml.safe_load`；校验器硬上限（`steps ≤ MAX_PLAN_STEPS=24`、`max_loops ≤ MAX_REVIEW_LOOPS`、
  step id ≤ 16 字符）+ V8 防注入；`workflows/` 只读挂载；`plans/` 由 `PlanStore.seal()` 写入即封存，
  改流程只能改 registry 或重放生成新 `plan_id`。
* 写库范围：Agent 只写 `evidence` 与 `msg_dedup`；`stage_runs` 与所有业务表只有编排层写。

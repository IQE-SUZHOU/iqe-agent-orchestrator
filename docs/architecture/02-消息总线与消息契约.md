# 02 消息总线与消息契约（RabbitMQ）

## 1. 总线选型（结论）

| 候选 | 契合度 | 成本 | 结论 |
|---|---|---|---|
| **RabbitMQ 4.1**（topic exchange + DLX） | 每 stage 一条 durable 队列、topic 通配、声明式死信、manual ack、自带管理 UI 与 Prometheus | 中 | ✅ **采用** |
| NATS JetStream | subject 原生、单二进制更轻、可回放；但 DLQ 需自研转发、无官方 UI | 低 | 备选（见 §12 差异对照） |
| Kafka | 回放强，但 stage-per-consumer 模型啰嗦，演示过重 | 高 | 不用 |
| Redis Streams | 上手快，但 ack/重投/DLQ/消费者组语义要自己补 | 低 | 不用 |

**采用 RabbitMQ 的理由**

1. **DLX 声明式死信**：毒消息/重试耗尽自动进 `q.dlq`，不需要自研 advisory 转发器。
2. **权限可按 exchange 强制架构约束**：只有 `ci-orch` 对 `ci.cmd` 有 write 权限，"只有编排层能下命令"由 broker 物理保证，而不是靠代码自觉。
3. **管理 UI（15672）**：演示与联调时直接看队列深度、unacked、消息内容、手动重投。
4. **Prometheus 插件开箱**：`rabbitmq_prometheus` 暴露队列指标，省掉自研 exporter。
5. 团队/运维更普遍，企业内大概率已有集群可复用。

**已知代价（必须在实施时正视）**

| 代价 | 说明 | 对策 |
|---|---|---|
| **无程序化回放** | 普通队列 ack 即删，不能像 JetStream 那样 `DeliverAll` 重放 | 真相源是 Postgres `stage_runs`；另设**审计影子队列**（§10.1）保留 7 天供人工查阅 |
| **无发布端去重** | 没有 `Nats-Msg-Id` 等价物，重发就是两条消息 | 由四层幂等（§7）吸收；消息属性带 `message_id` 便于 UI 检索 |
| 运行时更重 | Erlang VM，镜像 200MB+，内存 256–512Mi | 只部署 1 个节点；不追求演示档的极限轻量 |

## 3. Subject → (Exchange, Routing Key) 映射规则

**唯一规则**：subject 的前两段决定 exchange，**完整 subject 字符串即 routing key**。

```
ci.cmd.reviewer.gate2  →  exchange = ci.cmd    , routing_key = ci.cmd.reviewer.gate2
ci.result.reviewer     →  exchange = ci.result , routing_key = ci.result.reviewer
ci.event.case.triaged  →  exchange = ci.event  , routing_key = ci.event.case.triaged
ci.dlq.reviewer        →  exchange = ci.dlx    , routing_key = ci.dlq.reviewer
```

命令的第三段是 **mode**（闸门/动作），结果只按 **stage** 路由（`payload.status` 不参与路由）。

### 3.1 Subject 注册表（权威）

| Subject | 方向 | Payload | 说明 |
|---|---|---|---|
| `ci.cmd.monitor.scan` | orch → monitor | Command(monitor.scan) | 定时/手动扫描 CI 源（`mode=scan`） |
| `ci.cmd.triage.classify` | orch → triage | Command(triage.classify) | 根因分类与分流预判（`mode=classify`） |
| `ci.cmd.reviewer.gate1` | orch → reviewer | Command(reviewer.gate1) | 闸门 1：批准 internal / external |
| `ci.cmd.reviewer.gate2` | orch → reviewer | Command(reviewer.gate2) | 闸门 2：复核修复与验证 |
| `ci.cmd.reviewer.gate3` | orch → reviewer | Command(reviewer.gate3) | 闸门 3：复核工单 |
| `ci.cmd.remediation.fix` | orch → remediation | Command(remediation.fix) | 自动修复（4a） |
| `ci.cmd.reproduction.evidence` | orch → reproduction | Command(reproduction.evidence) | 受控复现取证（4b） |
| `ci.cmd.reproduction.verify` | orch → reproduction | Command(reproduction.verify) | 修复验证（5a） |

## 4. 消息信封（Envelope）

JSON Schema 见 [schemas/envelope.schema.json](../../orchestrator/src/iqe_orchestrator/common/data/schemas/envelope.schema.json)。业务字段不变，另映射到 AMQP 属性：

| Envelope 字段 | AMQP 属性 / Header | 说明 |
|---|---|---|
| `msg_id` | `properties.message_id` | ULID，UI/日志检索用 |
| `correlation_id` | `properties.correlation_id` | 全链路一致，UI 可按其过滤 |
| `msg_type` | header `msg_type` | `command` / `result` / `event` |
| `schema` | header `schema` | 版本闸门 |
| `idempotency_key` | header `idempotency_key` | 幂等层 1/4 的键；格式 `f"{case_id or run_id}:{step_id}:{attempt}"`（见 §7） |
| `attempt` | header `attempt` | 重试次数 |
| `ttl_ms` | header `ttl_ms` | 应用层超时（**不是** AMQP expiration） |
| `trace.traceparent` | header `traceparent` | 透传，不解析 |
| `payload` | message body（JSON） | 见 [schemas/stage-contracts.json](../../orchestrator/src/iqe_orchestrator/common/data/schemas/stage-contracts.json) |

发布约定：

```python
await exchange.publish(
    aio_pika.Message(
        body=json.dumps(env).encode(),
        delivery_mode=aio_pika.DeliveryMode.PERSISTENT,   # durable 队列必须
        message_id=env["msg_id"],
        correlation_id=env["correlation_id"],
        content_type="application/json",
        headers={"msg_type": env["msg_type"], "schema": env["schema"],
                 "idempotency_key": env.get("idempotency_key"),
                 "attempt": env.get("attempt", 1), "ttl_ms": env.get("ttl_ms", 30000),
                 "traceparent": env.get("trace", {}).get("traceparent")},
    ),
    routing_key=rk,
    mandatory=True,          # 无匹配队列立即报错，而不是静默丢弃
)
```

## 5. Result 的三种状态

```json
{ "stage": "triage", "status": "ok",        "output": { ... } }
{ "stage": "triage", "status": "retryable", "error": { "code": "timeout", "detail": "..." } }
{ "stage": "triage", "status": "blocked",   "error": { "code": "no_evidence", "detail": "..." } }
```

- `ok` → `stage_runs.done`，Case 按计划 `on` 路由前进。
- `retryable` → `stage_runs.failed`，编排层在重试窗口内 `attempt+1` 重发新命令（窗口公式见 03 §8.3）。
- `blocked` → `stage_runs.blocked`，不重试，Case → `blocked`，进入日报 OPEN 清单。
- `expired` → `stage_runs.expired`：Agent 侧发现 `age_ms(env) > ttl_ms` 时直接回 `expired`（`agents/src/iqe_agents/runtime.py:120-124`），不重试。
- **没有 result**（编排层 Future 超时）→ 该行落 `timeout`；Agent 迟到的结果把该行改判 `late`，不改 Case 结论（见 03 §8.4）。

> result status → `stage_runs` 状态的映射表在 03 §8.4，权威出处 `orchestrator/src/iqe_orchestrator/src/iqe_orchestrator/dispatch.py:22`（`RESULT_STATUS_TO_RUN`）。

> 注意：`retryable` 走的是**应用层重发**（编排层再 publish 一条 attempt+1 的新命令），不是 AMQP requeue。requeue 会把同一条消息立刻塞回队头，容易形成热循环，本设计不用它做业务重试。

## 6. 确认、重试、死信

### 6.1 Publisher Confirms（必须开）

| 位置 | 要求 |
|---|---|
| orchestrator 发命令 | `confirm_delivery` + `mandatory=True`；confirm 之后才写 `stage_runs.status=dispatched` |
| Agent 发 result | 同样开 confirm；confirm 失败 → 重发一次 → 仍失败则记 `result_publish_failed` 并让编排层超时兜底 |

不开 confirm 的后果：broker 未持久化就回成功，编排层以为已下发，实际命令丢失且无人知晓。

### 6.2 Consumer Ack 与 Prefetch

| 项 | 取值 | 说明 |
|---|---|---|
| ack 模式 | manual（`no_ack=False`） | 处理完成才 ack |
| prefetch | 见 §2.2 | 数字即单实例并发上限 |
| ack 时机 | `publish result` 成功**且**写完 `stage_runs` 之后 | 保证"结果先落地、命令后确认" |
| 崩溃未 ack | broker 自动 redeliver（`redelivered=true`） | 幂等层吸收重复 |

### 6.3 重试模型（两层，职责不重叠）

| 层 | 触发 | 动作 | 上限 |
|---|---|---|---|
| **业务重试（主）** | result=`retryable`，或编排层 Future 超时 | 编排层 `attempt+1` **重新 publish 新命令** | `STAGE_MAX_ATTEMPTS`=2 |
| **传输重试（兜底）** | Agent 进程崩溃/连接断开，消息未 ack | broker redeliver 同一条消息 | 见下 |

传输重试上限：

- **演示档（classic 队列）**：RabbitMQ 没有 `x-delivery-limit`，靠 header `x-retry-count` 自增；超过 3 次 → `basic_nack(requeue=False)` → 进 DLQ。
- **生产档（quorum 队列）**：原生 `x-delivery-limit=3`，无需自研计数。

### 6.4 死信（声明式，无需自研转发器）

Agent 队列统一配置：

```
x-dead-letter-exchange:    ci.dlx
x-dead-letter-routing-key: ci.dlq.<stage>
```

消息进入 `q.dlq` 的三种情形：

| 情形 | 触发方式 |
|---|---|
| 毒消息（schema 非法 / 解码失败） | Agent `basic_nack(requeue=False)`，不允许重试 |
| 传输重试耗尽 | `x-retry-count > 3` 或 quorum `x-delivery-limit` 超限 |
| 队列超长/TTL 过期（如配置） | 队列策略自动 |

`q.dlq` 中每条消息带 `x-death` header（原 exchange、原 rk、原因、次数），编排层订阅后（实现：`orchestrator/src/iqe_orchestrator/src/iqe_orchestrator/dispatch.py:180-205`）：

1. 归档一行 `dlq(stage, idempotency_key, case_id, reason, original_routing_key, redelivered, body)`；`reason` 由编排层自己判定（`envelope_invalid` / `expired` / `contract_violation: …` / x-death 的 reason / `consumer_rejected`，见 `dispatch.py:40-60`）
   > **原始 routing key 取法（RabbitMQ 4.3.6 实测）**：x-death 条目里是 **`routing-keys`（数组）**，没有单数 `routing-key`；
   > 而 `message.routing_key` 在 `q.dlq` 里已经是 `ci.dlq.<stage>`（DLX 重写的结果），**不能**当原始 rk。
   > 实现取 `x-death[0]["routing-keys"][0]` 落库（`dispatch.py:180-205`），验收实测这一列是 `ci.cmd.reviewer.gate1`。
2. 累加 `ci_dlq_total{stage}`
3. 对应的 `stage_runs` 行状态**不在这里改**：它仍由 dispatch 判定为 `timeout`（Future 超时）或 `failed`（result=`retryable`），迟到结果再改判 `late`（见 03 §8.4）
4. **是否重投由编排层决定**（`POST /api/cases/{id}/replay`），broker 不自动重排

## 7. 幂等与去重（四层）

**幂等键（唯一规则）**：`idempotency_key = f"{case_id or run_id}:{step_id}:{attempt}"`（实现：`orchestrator/src/iqe_orchestrator/common/envelope.py:94`；schema 校验 `orchestrator/src/iqe_orchestrator/common/data/schemas/envelope.schema.json:21` 的 pattern `^[A-Za-z0-9_-]+:[a-z][a-z0-9_]*:[0-9]+$`，`attempt` 上限 5 见同文件第 20 行）。Monitor 扫描没有 `case_id`，用 `run_id`，且固定为 `"<run_id>:scan:1"`（实现：`orchestrator/src/iqe_orchestrator/scan.py:28-32` → `step_id="scan"`、`attempt=1`、`case_id=None`）。同一 `(case_id 或 run_id, step_id)` 的 `attempt` 全局单调递增（窗口与回放播种见 03 §8.3），所以键天然唯一。

> **Monitor 的记账口径**：Monitor **不是 plan step**（计划里的 stage 白名单不含 monitor，validator V2 直接禁止），它只由 Scheduler 定时或 `POST /api/scan` 触发。它的 `stage_runs` 行因此是「无主行」：`case_id = NULL`、`scan_id` 非空、`step_id = 'scan'`、`attempt = 1`（建表见 `orchestrator/src/iqe_orchestrator/migrations/001_init.sql:39-55`，`case_id` 可为 NULL；写入见 `orchestrator/src/iqe_orchestrator/common/db.py:139-150`）。日报命令同理：`step_id='daily1'`、`case_id=NULL`（`orchestrator/src/iqe_orchestrator/reporting.py:15-21`）。

| 层 | 机制 | 判据 |
|---|---|---|
| Agent 消费层（`msg_dedup` claim） | 处理前查 `msg_dedup(idempotency_key)`；已存在 → ack 丢弃 | 同一 `idempotency_key`（即同一 `(case_id 或 run_id, step_id, attempt)`）只跑一次 |
| Agent 结果层 | 查 `stage_runs` 是否已有同 `idempotency_key` 或 `attempt ≥ 收到 attempt` 的 `done` → ack 丢弃 | 防止编排层重启后重复投递导致重复复现/重复开单 |
| 编排层结果层 | 收到 result 按 `stage_runs.idempotency_key` UNIQUE 落库；重复 result → 忽略 | broker redeliver 不重复推进状态 |
| 发布层（publish 先于 ack） | 先 `publish` 拿到 publisher confirm 再 `ack`；发布失败不 ack | 不会出现「命令已 ack 但没发出去」，broker 会 redeliver |

`msg_dedup` 保留 7 天（后台定时清理）。业务侧兜底（副作用层）：`tickets(case_id, backend)` 唯一索引 —— 一个 Case 在同一工单后端只能有一张单。

> 与 JetStream 的差别：**没有发布端去重**。同一条命令若被重复 publish（编排层重试 bug、脚本手动重发），broker 会老老实实投两条，全部由上面第 1–3 层吸收。因此 `idempotency_key` 的正确性从"优化项"变成"正确性前提"。

## 8. 事件（ci.event）的使用边界

- **允许**：Agent 订阅 `ci.event.case.*` 维护本地台账/缓存（Ticketing 缓存近期 signature 查重、Monitor 缓存已知签名降噪）。
- **禁止**：用事件触发新的流水线阶段（路由权在编排层）。
- 事件**只由编排层发布**（没有任何 Agent 调用 `publish_event`）：状态跃迁发 `ci.event.case.<status>`，终态发 `ci.event.case.<terminal>`（带 `terminal_from`），建 Case 后发 `ci.event.case.created`。事件名里不带 stage/mode，避免与命令 subject 混淆。
- 事件不设 DLX：事件丢失不影响正确性，只影响缓存新鲜度。

## 9. 权限矩阵（vhost `/ci`）

| User | configure | write（exchange） | read（queue） |
|---|---|---|---|
| `ci-orch` | `^q\.(orch\|dlq\|audit)\..*` | `ci.cmd`、`ci.event` | `q.orch.results`、`q.orch.events`、`q.dlq` |
| `ci-agent-monitor` | — | `ci.result` | `q.agent.monitor` |
| `ci-agent-triage` | — | `ci.result` | `q.agent.triage` |
| `ci-agent-reviewer` | — | `ci.result` | `q.agent.reviewer` |
| `ci-agent-remediation` | — | `ci.result` | `q.agent.remediation` |
| `ci-agent-reproduction` | — | `ci.result` | `q.agent.reproduction` |
| `ci-agent-regression` | — | `ci.result` | `q.agent.regression` |
| `ci-agent-ticketing` | — | `ci.result` | `q.agent.ticketing` |
| `ci-agent-reporting` | — | `ci.result` | `q.agent.reporting` |
| `ci-admin`（仅运维/初始化） | `.*` | `.*` | `.*` |

> **实现对照**（`tools/setup_broker.py:52-71`，账号名用下划线：`ci_orch` / `ci_agent_<stage>`）：`ci_orch` 的 write = `ci.cmd` / `ci.event` / `ci.dlx` + 各队列（RabbitMQ 把 `queue.bind` 记为对队列的 write，所以拓扑声明只能由编排层做）；每个 Agent 账号的 write **只有 `ci.result`**，read 只有自己的 `q.agent.<stage>`，configure 只有自己的队列 + `ci.result`。也就是说「只有编排层能发事件」在 V1 同样是物理约束。

这套权限把架构约束变成物理约束：

- Agent **没有** `ci.cmd` 的 write 权限 → 想私自下发命令，broker 直接拒绝（403）。
- Agent 读不到别人的队列 → 无法窃取/抢单其他阶段的任务。
- orchestrator 读不到 `q.agent.*` → 强制只通过 result 感知 Agent 状态。

## 10. 可观测性（补偿"无回放"）

### 10.1 审计影子队列

`q.audit.results` / `q.audit.events` 绑定与正式队列相同的 rk，但**没有消费者**：
消息永不被 ack，只按 `x-message-ttl` 过期（7d / 30d），`x-max-length` 封顶防止写满磁盘。

得到的能力：

| 能力 | 做法 |
|---|---|
| 回看某 Case 的全部结果消息 | UI 15672 → `q.audit.results` → Get messages（按 `correlation_id` 过滤，或 CLI `rabbitmqadmin get`） |
| 对比"消息内容 vs 库里落库内容" | 同上，用于排查序列化/截断问题 |
| 复盘某次异常链路 | `q.dlq` + `q.audit.*` 三处对照 |

**边界（明确写清，避免误用）**：这是**人工查阅**，不是程序化回放。编排层不能"从审计队列重放整条链路"——重放走 `POST /api/cases/{id}/replay`，基于 `stage_runs` 重新发命令（见 03 §9）。

### 10.2 指标

`rabbitmq_prometheus`（`:15692`）直接提供，不需要自研：

| 指标 | 用途 |
|---|---|
| `rabbitmq_queue_messages_ready{queue}` | 积压 |
| `rabbitmq_queue_messages_unacked{queue}` | 在飞 |
| `rabbitmq_queue_messages_published_total{queue}` | 投递总量（D1 判据） |
| `rabbitmq_queue_messages_acked_total{queue}` | 消费总量 |
| `rabbitmq_queue_consumers{queue}` | 消费者掉线告警 |

## 11. 兼容与演进

- `schema` header 做版本闸门：Agent 收到 `schema != v1` → `status=blocked, code=schema_mismatch`。
- 新增信封字段一律可选、向后兼容；破坏性变更换 `ci2.` 前缀并行部署（新 exchange 组 `ci2.cmd/ci2.result/...`，可双跑对比）。
- **队列参数不可原地改**（prefetch 除外）：改 DLX、TTL、类型需删队列重建；生产变更用"新队列 + 新 binding + 旧队列排空后删除"的三步法。
- **计划层不改变总线契约**：Plan（workflow / LLM 生成）是编排层内部产物，以 YAML 落盘（`workflows/` + `plans/`），**不新增 exchange / queue / subject，也不上总线**；对 Agent 而言命令与结果形状完全不变（见 03 §2）。

## 12. 与 NATS 方案的差异对照（变更记录）

| 维度 | NATS JetStream（原方案） | RabbitMQ（本方案） |
|---|---|---|
| 路由单元 | subject（stream 捕获） | exchange + routing key（rk 复用完整 subject） |
| 每 stage 队列 | Stream + durable consumer | durable queue + binding |
| 死信 | 自研：监听 advisory → 转发 `ci.dlq.*` | 声明式 `x-dead-letter-exchange` |
| 发布端去重 | `Nats-Msg-Id` + `duplicate_window` | 无（靠四层幂等） |
| 历史消息回放 | 原生 `DeliverAll` / 按时间序号 | 无；用审计影子队列 + `stage_runs` 补偿 |
| 投递次数上限 | `max_deliver` | classic 自研 `x-retry-count`；quorum `x-delivery-limit` |
| 流控 | `max_ack_pending` | `basic_qos(prefetch_count)` |
| 权限粒度 | subject 级 publish/subscribe | exchange 级 write + queue 级 read |
| 管理界面 | 无官方 UI | 自带 15672 |
| 监控 | `/varz` `/jsz` + exporter | `rabbitmq_prometheus` 原生 |
| 部署体积 | 单二进制 ~20MB | Erlang 运行时，镜像 ~200MB |

业务契约（subject 字符串、envelope 字段、result 三态、幂等键、路由规则）**全部不变**，Agent 与编排层的业务代码只需替换 SDK 层。

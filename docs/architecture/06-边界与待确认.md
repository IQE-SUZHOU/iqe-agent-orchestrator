# 06 边界、替换点、风险与待确认

## 1. 本设计刻意不做什么

| 不做 | 原因 | 何时再考虑 |
|---|---|---|
| Agent 真实能力（Jenkins 轮询、真实 rebuild、真实 Jira/ADO 写入） | 本轮只验交互层与编排骨架 | 契约冻结后逐个替换工具层（§2） |
| 编排层多副本高可用 | 单活 + checkpointer 已够演示；Dispatch–Await 的 Future 是进程内的 | Case 量上千/日时按 `case_id` 分片，或把结果改成表的轮询 |
| Kafka / 事件溯源 / 流处理 | 重，收益不明 | 需要长期回放与离线分析时 |
| 工单人工审批 UI | 演示不需要：`TICKET_AUTOCREATE=false` 时 Ticketing 只回 `ticket_status=drafted` | 真要审批回路，先加事件发布点与审批端点，再改 plan 路由 |
| Agent 间点对点通信 | 破坏可审计性 | 永不做（架构约束） |
| 对象存储、Loki/Grafana、OTel 全链路 | 演示用 Postgres + JSON 日志 + Prometheus 文本即可 | 生产化时替换 |
| 语义查重（embedding） | Mock 用 signature + 关键词已演示 | 工单量大、签名不稳时 |
| 运行时人工临时编排（给单个 Case 手改路径） | 破坏"执行确定性 + 可审计" | 永不开放；人工参与只通过 `workflows/*.yaml` + PR |
| LLM 自由 DAG / 自由工具调用 | 只需要"选哪几个 step"，自由拓扑无法穷举校验 | 先扩 `plan.schema.json`，再放开 |
| 计划多版本并行/灰度（同一 Case 双跑） | 会翻倍副作用 | 以 `ci2.` 前缀并行而非同 Case 双跑 |

## 2. 从 Mock 到真实的替换点（契约不变，只换内部）

| Agent | Mock 部分 | 真实替换 | 契约影响 |
|---|---|---|---|
| Monitor | `_load_feed` 读 `fixtures/ci_feed/*.json` | Jenkins REST（`builds` / `wfapi` / JUnit）或 webhook | 无（`observations[]` schema 不变） |
| Triage | 规则表给 `rca / confidence / path` | LogDistiller + 分类技能 + 1 次 LLM 判定；知识库换向量检索 | 无 |
| Reviewer | 夹具覆盖 `verdict` / `decision` | 保留机械预检（护栏），模型只填 `quality_scores` 与 `notes` | 无 |
| Remediation | 按组件模板生成 diff 摘要 | git 工作区改动 + ADO 工作项 + 变更审批流 | 无 |
| Reproduction | 假复现矩阵 | Jenkins Lockable Resources 锁机 + 同参重跑 + 抓 console | 无；需新增 Jenkins 凭据与机位配额 |
| Regression | 夹具给基线与 patch | 基线库查询 + 逐提交触发流水线二分 + 提交元数据关联 | 无 |
| Ticketing | 假单号（`jira-mock`） | Jira/Azure REST（search 查重 → create → 状态回采） | 无；新增 `backend` 配置与 token |
| Reporting | 模板 + Postgres 聚合 | 已足够真实，可直接实现，成本最低 | 无 |

**建议顺序**：Reporting → Monitor → Triage → Ticketing → Reviewer → Remediation → Regression → Reproduction
（破坏性最低优先，最后才开放"会占重跑机器"的能力）。

## 3. 风险与缓解

| # | 风险 | 缓解 |
|---|---|---|
| R1 | at-least-once 导致重复复现/重复开单 | 四层幂等（`msg_dedup` / `stage_runs` 唯一键 / `tickets(case_id,backend)` 唯一 / 先发布后 ack）+ D9 演示 |
| R2 | 编排层单点 | 单活 + Postgres checkpointer；重启不自动续跑在飞 Case，靠 `POST /api/cases/{id}/replay` 人工推进 |
| R3 | Agent 静默失败导致 Case 永挂 | `TTL_MS` + `STAGE_TIMEOUT_S` + `attempt` 上限 → `blocked` 并进日报 OPEN |
| R4 | LLM/规则误判根因 | 闸门机械预检（gate1 4 项 / gate2 6 项 / gate3 5 项）+ `confidence ≥ 0.70` 门槛 |
| R5 | 回炉拉锯（gate1 ↔ triage、gate2 ↔ 4a） | `max_loops ≤ MAX_REVIEW_LOOPS=2` + `RECURSION_LIMIT=40`，超限直接 `blocked` |
| R6 | subject 配错导致消息静默滞留 | 契约 `command_subject` 与 `bus.AGENT_QUEUES` 同源，`ci-broker-setup` 幂等声明；`/readyz` 检查拓扑 |
| R7 | 大日志把上下文撑爆 | LogDistiller 硬预算，证据只存摘要 + 引用（全文进 evidence 表） |
| R8 | 总线单节点故障 | PVC + durable queue；生产切 quorum 队列 |
| R9 | Mock 与真实实现行为差异掩盖缺陷 | JSON Schema 双向校验（Agent 入参 + 编排层出参）+ 契约测试 |
| R10 | 无消息回放（ack 即删） | 真相源 `stage_runs`；`q.audit.*` 保留 7d/30d；重放走 `POST /api/cases/{id}/replay` |
| R11 | 队列参数不可原地修改（DLX/TTL/类型） | 「新队列 + 新 binding + 旧队列排空后删除」三步法；破坏性变更升 `ci2.` 前缀 |
| R12 | LLM 生成非法计划（不存在的 stage / 回环 / 跳过闸门） | `validate_plan` V0–V9；两次不通过 → `degraded` 内置安全网；非法计划永不执行 |
| R13 | LLM 被 CI 日志注入 | 观测摘要硬截断；模型不看队列名/地址；V8 禁止 `rationale` 携带 subject/URL/命令字面量 |
| R14 | LLM 不可用时拖慢链路 | `PLAN_MODE=strict` 直接走内置安全网；`auto` 下两次失败同样降级并标 `degraded=true` |
| R15 | 计划与 stage 契约漂移 | `plan.validator` 带版本；契约升版时批量复验 `plans` 表；`yaml_sha256` 可追到具体文件 |
| R16 | 人工 YAML 写错（比模型更容易写死循环） | 人工与模型共用同一 validator；registry 启动时逐条加载，**解析失败只跳过该条**并记 `workflow_load_failed` |

| 阶段 | 交付 | 判据 |

## 5. 待确认

| # | 问题 | 默认选择 | 备选 |
|---|---|---|---|
| Q1 | 总线选型 | ✅ **已定：RabbitMQ 4.1**（topic exchange + 声明式 DLX、管理 UI、按 exchange 强制权限；无程序化回放，用 `q.audit.*` + `stage_runs` 补偿） | NATS JetStream |
| Q2 | 部署形态 | **docker-compose / run_local 单机演示**，K8s 清单作为交付形态 | 直接上内网 K8s |
| Q3 | Mock 数据来源 | 读 `fixtures/**` + env 场景切换（可复现、可脚本化） | 纯随机（不可复现，不推荐） |
| Q4 | 工单是否需要人工批准回路 | 默认 `TICKET_AUTOCREATE=true`，保留 `drafted` 状态 | 加审批端点 + 事件（当前未实现） |
| Q5 | LLM 端点/模型 | OpenAI 兼容端点 + 小模型；演示走 `MOCK_LLM_ENABLED=true` 夹具 | 复用公司 LLM 网关（需确认配额与审计） |
| Q6 | 谁审 `workflows/*.yaml` | 架构师 1 人 + 值班 1 人（两人 approve），变更即 `version+1` | 线上自助编辑（破坏"定义即代码"，不推荐） |
| Q7 | 启动恢复扫描 / `workflows/reload` 原子切换 | 先只做离线校验（CI 里跑校验器）；线上靠重启生效 + replay 兜底 | 两个都实现（`stage_runs` 加租约/心跳，改动较大） |
| Q8 | 计划文件持久化 | K8s 现在挂 `emptyDir: /var/lib/ci-triage`，Pod 重启即丢封存文件 | 换 PVC；或把 plan 正文直接进 `plans.steps`（列已有），文件只作调试 |
| Q9 | 表清理任务 | 加每日任务：`msg_dedup` 保留 7d、`stage_runs` 保留 90d，与 `q.audit.*` TTL 对齐 | 分区表 + 自动裁剪；演示阶段可先不做 |

> 另有两处真实场景待补：CI 源是单实例还是多实例 Jenkins；Jira 与 Azure DevOps 先做哪一个。
> 这两项只影响 Agent 工具层，不影响本架构与消息契约。

## 6. 已定稿的评审结论（实现期回写）

以下 7 项已在实现期核对代码并定稿，**文档里凡与本文冲突处，以本表为准**：

| # | 定稿结论 | 写在哪儿 | 代码出处 |
|---|---|---|---|
| 1 | **`payload.mode` 值域以 `stage-contracts.json` 的 `x-mode-authority` 为权威**：8 个 stage / 13 个 mode（monitor=scan；triage=classify；reviewer=gate1\|gate2\|gate3；remediation=fix；reproduction=evidence\|verify；regression=check\|bisect；ticketing=create；reporting=case\|daily）。**routing key 第三段就是 mode**：`ci.cmd.<stage>.<mode>`；result 只按 stage：`ci.result.<stage>` | 02 §2–§3.1、03 §8.1、04 §3、05 §1 | `common/data/schemas/stage-contracts.json`；`common/contracts.py::MODE_AUTHORITY`；`dispatch.py::dispatch` |
| 2 | **`idempotency_key = {case_id 或 run_id}:{step_id}:{attempt}`**。Monitor 扫描没有 Case：键为 `{run_id}:scan:1`，`stage_runs` 行是 `case_id=NULL` + `scan_id` 非空 + `step_id='scan'` + `attempt=1`；日报同理 `{run_id}:daily1:1`。Monitor **不是 plan step**（V2 禁止） | 02 §7、03 §8.3、05 §1 | `common/envelope.py::make_command`；`scan.py`；`reporting.py` |
| 3 | **闸门机械预检以 `checks[i].id` 为契约编号**：gate1 4 项（`evidence_present` / `triage_confident` / `path_known` / `loop_not_exhausted`）、gate2 6 项、gate3 5 项。"不适用"不是新状态：仍进 `checks[]`，`pass=true` + `detail` 写明跳过。`check` 元素字段固定为 `id / name / pass / detail / reason_code` | 04 §3.3、03 §6（V9） | `agents/reviewer/playbook.py`（`_check` / `_gate1..3`） |
| 4 | **attempt 在 Case 生命周期内单调**：单次访问窗口是 `attempt_prev+1 .. attempt_prev+max_attempts`；回炉后再进入同一步拿到更大 attempt，因此幂等键天然不同。**重放复用「计划」不复用「attempt」**：`attempts` 用 `db.max_attempt_by_step(case_id)` 播种，`gen+1`、`cursor=0`、无 `?from=` | 03 §5.3、§8.3、§9 | `graph.py::_step` / `replay_case`；`common/db.py` |
| 5 | **`stage_runs` 终态映射定稿**：`{ok→done, blocked→blocked, retryable→failed, expired→expired}`；编排层超时（无 result）直接落 `timeout`；超时后才到的结果把该行改判 `late`（不改 Case 结论）；DLQ 只归档 `dlq` 表，不改 `stage_runs` 状态；没有 `running` / `skipped` | 02 §5、03 §8.2、05 §1 | `dispatch.py::dispatch` / `RESULT_STATUS_TO_RUN`；`common/db.py` |
| 6 | **HTTP 端点权威清单在 05 §4.1**：业务 API 一律 `/api/*`，Web UI 是 `/` 与 `/ui/*`（同进程同端口）。`/trigger/*`、`/cases/*`、`/admin/workflows*` 全部作废；`replay` 无 `from` 参数；`/api/workflows/reload` **未实现** | 05 §4.1、03 §11 | `orchestrator/app.py` |
| 7 | **事件只由编排层发布**，实际只有一族：`ci.event.case.created`（建 Case）、`ci.event.case.<活状态>`（每步成功后，如 `triaged` / `remediated` / `fix_verified` / `reproduced` / `regression_checked` / `bisected` / `ticketed` / `ticket_approved` / `reported`）、`ci.event.case.{blocked\|closed\|closed_rejected}`（终态带 `terminal_from`）。Agent 账号没有 `ci.event` 写权限 | 02 §3.1、§8–§9；03 §5.4 | `graph.py::_step` / `_finalize`；`scan.py`；`tools/setup_broker.py` |

> 除上表 7 项，本文 §1 边界、§2 替换点、§3 风险、§4 节奏、§5 待确认（含 Q7–Q9）仍是待确认状态。

# 06 边界、替换点、风险与待确认

## 1. 本设计刻意不做什么

| 不做 | 原因 | 何时再考虑 |
|---|---|---|
| Agent 真实能力（Jenkins 轮询、真实 rebuild、真实 Jira/Azure 写入） | 本轮只验交互层 | 契约冻结后逐个替换工具层（§2） |
| 编排层多副本高可用 | 单活 + checkpointer 恢复已够演示 | Case 量 > 500/日时按 `case_id` 分片或 lease 表 |
| Kafka / 事件溯源 / 流处理 | 重，收益不明 | 需要长期回放与离线分析时 |
| 工单人工审批 UI | 演示不需要 | `TICKET_AUTOCREATE=false` 时 Ticket 只回 `ticket_status="drafted"`（`agents/ticket/playbook.py:105`）；**事件口 `ci.event.ticket.drafted` V1 未实现**（见 §6 定稿结论） |
| Agent 间点对点通信 | 破坏可审计性 | 永不做（架构约束） |
| 对象存储、Loki/Grafana、OTel 全链路 | 演示用 Postgres + JSON 日志 + Prometheus 文本即可 | 生产化时替换 |
| 语义查重（embedding） | Mock 用 signature + 关键词已演示 | 工单量大、签名不稳时 |
| 运行时人工临时编排（给单个 Case 手改路径） | 破坏"执行确定性 + 可审计"，且与 workflow 定义重复 | 永不开放；人工参与只通过 `workflows/*.yaml` + PR |
| LLM 自由 DAG / 自由工具调用 | 只需要"选哪几个 stage"，不需要任意拓扑；自由拓扑无法穷举校验 | 出现真正无法用"序列 + 条件跳转"表达的场景时，先扩 schema 再放开 |
| 计划的多版本并行/灰度（同一 Case 双跑对比） | 演示不需要；且会翻倍副作用 | 生产做流程改造 A/B 时，以 `ci2.` 前缀并行而非同 Case 双跑 |

## 2. 从 Mock 到真实的替换点（契约不变，只换内部）

| Agent | Mock 部分 | 真实替换 | 契约影响 |
|---|---|---|---|
| Monitor | `MOCK_FEED_SOURCE` 读 JSON | Jenkins REST 轮询（builds/wfapi/JUnit）或 webhook | 无（`observations[]` schema 不变） |
| Triage | 剧本给 `rca/confidence` | LogDistiller 真实蒸馏 + SKILL Playbook + 1 次 LLM 判定；Jarvis CLI 只读白名单 | 无；新增 `evidence_gaps` 已在 schema |
| Reproduction | 假 rebuild 列表 | Jenkins rebuild（同参、锁机、配额、熔断） | 无；需新增 Jenkins 凭据与 allowlist 配置 |
| Ticket | 假单号 | Jira/Azure API（search 查重 → create → 状态回采） | 无；新增 `backend` 配置与 token |
| Reviewer | 剧本 verdict | 机械预检（已定义 8 条）+ 1 次独立 LLM 复核 | 无；建议独立模型端点 |
| Reporting | 剧本数字 | Postgres 聚合已足够真实（可直接实现，成本最低） | 无 |

**建议顺序**：Reporting → Monitor → Triage → Ticket → Reviewer → Reproduction（破坏性最低优先，最后才开放会重跑机器的能力）。

## 3. 风险与缓解

| # | 风险 | 缓解（已在本设计中） |
|---|---|---|
| R1 | at-least-once 导致重复复现/重复开单 | 三层幂等（`msg_dedup` / `stage_runs` 唯一键 / `tickets(case_id,backend)` 唯一）+ D6 演示验证 |
| R2 | 编排层单点 | 单活 + Postgres checkpointer（`thread_id={case_id}#{gen}`）。**实现期修正**：V1 没有"启动恢复扫描"，重启不会自动续跑在飞的 Case，未收口的靠 `POST /api/cases/{case_id}/replay` 人工推进（见 §5 Q7） |
| R3 | Agent 静默失败导致 Case 永挂 | `ttl_ms` + `STAGE_TIMEOUT_S` + `attempt` 上限 → `blocked` 并进日报 OPEN |
| R4 | LLM 误判根因 | Reviewer 机械预检 8 条 + `confidence` 门槛 + 结论必须挂 `evidence_refs` |
| R5 | 循环拉锯（Reviewer ↔ Triage） | `MAX_REVIEW_LOOPS=2` + `recursion_limit=14` |
| R6 | subject 配错导致消息静默滞留 | 启动自检：Agent 订阅清单 vs 编排层发布清单比对，缺配直接失败 |
| R7 | 大日志把上下文撑爆 | LogDistiller 硬预算（`CI_DISTILLED_CHARS`），证据只存摘要 + 引用 |
| R8 | 总线单节点故障（单节点 RabbitMQ 不做复制） | PVC + durable queue；生产切 quorum 队列（3 副本 Raft），单节点只用于演示 |
| R9 | Mock 与真实实现行为差异掩盖设计缺陷 | 契约用 JSON Schema 双向校验（Agent 入参校验 + 编排层出参校验），CI 跑契约测试 |
| R10 | **无消息回放**：普通队列 ack 即删，无法重放整条链路 | 真相源 `stage_runs`；`q.audit.results`/`q.audit.events` 分别保留 7d/30d 供人工查阅；重放走 `POST /api/cases/{case_id}/replay`（基于 DB，不依赖总线；无 `from=<stage>`，见 03 §9） |
| R11 | 队列参数不可原地修改（DLX / TTL / 类型） | 变更走「新队列 + 新 binding + 旧队列排空后删除」三步法；破坏性变更升 `ci2.` 前缀 |
| R12 | **LLM 生成非法计划**（不存在的 stage / 死循环跳转 / 跳过复核） | JSON Schema + V1–V8 双闸门；失败重试 1 次；仍失败落 `degraded` 安全网（s2_full / s1_lite），非法计划永不执行 |
| R13 | **LLM 被 CI 日志注入**（日志里写着"执行 X"） | 观测摘要硬截断；模型不看队列名/地址；计划 schema 只允许 stage 枚举，V8 禁止 rationale/mode 携带 subject/URL/命令字面量 |
| R14 | **LLM 不可用/超时**拖慢整条链路 | `PLAN_TIMEOUT_S=8` 直接判失败 → 安全网计划，Case 照常推进；`PLAN_MODE=strict` 时改为 `blocked` 并告警 |
| R15 | **计划与 stage 契约漂移**（改名后历史计划失效） | `plan.validator` 带版本；契约升版时批量复验 `plans` 表；`plans` 行保留 `yaml_sha256` 可追到具体文件 |
| R16 | **人工 YAML 写错**（比模型更容易写死循环） | 人工与模型共用同一 validator（`plan.py::validate_plan`，V0–V8）。**实现期修正**：V1 没有 `/admin/workflows/reload`，也没有"全通过才生效"的原子切换——registry 在启动时逐条加载，**解析失败的那一条被跳过并记 `workflow_load_failed`**，其余照常上线；运行期计划过不了 validator 则 `plan_violations` → 不执行 + 降级安全网。"整体拒绝启动/整体回滚"列入 §5 Q7 |

## 5. 待确认（1 项已定 + 8 项待定：Q1–Q6 是原设计问题，Q7–Q9 是实现期新增）

| # | 问题 | 我的默认选择 | 备选 |
|---|---|---|---|
| Q1 | 总线选型 | ✅ **已定：RabbitMQ 4.1**（topic exchange + 声明式 DLX 自动死信、管理 UI、按 exchange 强制权限；代价是无程序化回放，用 `q.audit.*` + `stage_runs` 补偿，详见 02 §1/§12） | 回退 NATS JetStream：若后续确认需要程序化回放或极致轻量运维 |
| Q2 | 部署形态？ | **docker-compose 单机演示**，K8s 清单作为附录 | 直接 K8s（内网集群 + Harbor 镜像） |
| Q3 | Mock Agent 的「假数据」来源？ | 读 `fixtures/*.json` + env 剧本切换（可复现、可脚本化） | 纯随机生成（演示不可复现，不推荐） |
| Q4 | 工单是否需要人工批准回路？ | 演示默认 `TICKET_AUTOCREATE=true`，保留事件口 | 演示就演示审批（加 `POST /api/cases/{case_id}/ticket/approve`，**当前未实现**；`drafted` 状态已可用，缺的是事件与审批端点） |
| Q5 | LLM 兜底用哪个端点/模型？ | **OpenAI 兼容端点 + 小模型**（`PLAN_MODEL` 与 Agent 内部模型解耦），演示走 `MOCK_LLM_ENABLED=true` 的 YAML 剧本 | 复用公司统一 LLM 网关（需确认配额与审计要求） |
| Q6 | 谁来审 `workflows/*.yaml`？ | **架构师 1 人 + 值班 1 人**（两人 PR approve），变更即版本号 +1 | 线上自助编辑（曾写作 `POST /admin/workflows` 直写 DB，**未实现**；现只有只读的 `GET /api/workflows`）：快，但破坏"定义即代码"，不推荐 |
| **Q7** | **两处"设计目标级"闸门要不要补进 V1.1？**（① 编排层启动恢复扫描：重启后自动续跑在飞 Case；② `POST /api/workflows/reload` 的"全通过才生效"原子切换） | 先补 ② 的离线校验（CI 里跑 `tools/` 校验 YAML，PR 阶段拦住），线上仍靠重启生效；① 用 `POST /api/cases/{case_id}/replay` 顶住，不自动续跑 | 两个都实现：①需要给 `stage_runs` 加租约/心跳，改动不小，等 Case 量上来再说 |
| **Q8** | **计划文件的持久存储**：K8s 现在给编排层挂的是 `emptyDir`（`/var/lib/ci-triage`），Pod 重启即丢封存 plan 文件 | 换 PVC（并把 `PLANS_DIR` 指过去），否则重放只能靠 `plans` 表索引重新实例化 | 把 plan 正文直接存进 `plans` 表（`steps` 列已有），文件只作调试产物 |
| **Q9** | **表清理任务缺失**：`msg_dedup` 只增不清，`stage_runs` 也没有过期清理 | 加一条每日任务（`msg_dedup` 保留 7 天、`stage_runs` 保留 90 天），与 `q.audit.*` 的 TTL 对齐 | 用分区表 + 按时间自动裁剪；演示阶段可先不做 |

> 另有两处真实场景待补：CI 源到底是 Jenkins（单实例还是多实例）；Jira 与 Azure DevOps 先做哪一个。这两项只影响 Agent 工具层，不影响本架构与消息契约。

## 6. 已定稿的评审结论（实现期回写）
